# Order processing implementation review

Review the [architecture](../../../architecture.md) alongside the
[local test plan](../../../TESTING.md).

| Area | Design consideration | Implementation / local check |
| --- | --- | --- |
| Money | A region change must not reinterpret existing prices. | Persist one catalog currency and snapshot converted prices on quotes/orders. Test exact arithmetic, expiry and legacy adoption. |
| Concurrency | Cancellation and processing can compete for one order. | Conditional updates and row locks; test races, locked rows and batch rollback. |
| Worker health | A reachable API can have a failing worker. | Include failure/staleness in readiness; test startup, failure and recovery. |
| Retry safety | A lost response can cause duplicate purchases. | Customer-scoped idempotency keys and atomic request/order persistence; test concurrency and payload conflicts. |
| Authentication | Public password checks consume resources and can reveal account existence. | Equivalent password-check paths, bounded auth work and process-local throttling. |
| Traceability | Logs must describe committed actions without exposing credentials. | Structured request/mutation logs and redaction tests. |
| HTTP boundaries | Malformed IDs and bodies must return controlled errors. | Strict JSON binding, explicit UUID parsing and handler tests. |
| Local testing | Unit tests cannot exercise database locking or container startup. | Run integration tests with PostgreSQL and `make acceptance` with Docker. |

Known boundaries: no inventory reservation, payment workflow, durable status
history or global worker scheduler. Production capacity and failover require
separate load and deployment testing.
